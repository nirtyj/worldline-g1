# M2: Worldline on the G1 stack

Status: **M2a done (offline, 2026-09-29).** Worldline's runtime runs end to end on the new robot API, on the laptop,
with no simulator, no model and no keys. One command runs "Bring me the alarm clock." in H40 through the page server,
the harness, System 1, the planner, the services and the lite body, and scores it on world truth: `PASS*` (a labelled
fallback pass, `lite` executor). The full suite gives **477 passed, 1 skipped, 1 deselected** (the opt-in live
check), in about 60 s. **M2b** is the live run: Worldline driving the SONIC-walking G1 in Isaac, with scripted arms
and GR00T in `manipulate`. §7 lists the M2b tasks.

## 2. How to run it (laptop, offline)

```bash
uv venv --python 3.11 .venv-rt
uv pip install --python .venv-rt/bin/python numpy scipy pillow pyzmq msgpack websockets pyyaml pytest \
    "google-genai==2.25.0" "typesafe_sdk==0.7.2"

.venv-rt/bin/python -m pytest                          # every suite (unit, contract, kept, world, services, ui, eval)
.venv-rt/bin/python -m eval.offline_episode            # the M2a episode: prints the timeline, the checks, the verdict
.venv-rt/bin/python -m eval.offline_episode --out docs/traces/m2a_offline_f1_h40   # re-record the committed trace

# the page, offline: no keys, no model (open http://127.0.0.1:8765, type "Bring me the alarm clock.")
.venv-rt/bin/python -m ui.server --profile lite --scene procthor-train-40 \
    --planner brains.scripted:create --system1 tests.kept.system1_stub:create --speed 5
```

        ├─ System 1: tests/kept/system1_stub.py   labels "bring me the ..." (request, target), gets head frames
        │                                          through the G1_HEAD frame gate, reports one observation

What the runner checks (all pass):

- **The F1 shape (PLAN 2.2), in order.** System 1 labels the request; navigate; arrival scan; `check_reachability`
  binds `alarm_clock_1`, then says it is reachable (after a `needs_reposition` → `navigate(reach_stance)` → check
  again); pick; verify glance; navigate to the user; place; `goal_check` ok; `delivered`.
- **The contract.** Every result carries an `observation_id`. Envelope statuses are lowercase. Every `manipulate`
  names its executor and skill. Every stepping-stone result says `fallback` in the line the planner reads.
- **System 1.** It got gated head frames (3 at speed 40, 5-6 at slower speeds), was asked to observe, and its
  observation reached the runtime as a NOTICED hint (never as an object fact).
- **Honesty.** The pass is a target pass only if every body result came from a target executor
  (`api.results.is_target`). On lite it is `PASS*`: a fallback pass.

The episode is `tests/eval/test_offline_episode.py`, so every `pytest` run repeats it.

### 5.2 Protocols aligned with their implementations

The Protocols in `api/services.py` had drifted from what `world/` and `services/` implement, and `world/model.py`
kept a second, different copy. What changed:

- `api/services.py` now describes the real surfaces:
  - each service's non-blocking `start(...)`;
  - `ManipulationService.capability` and `start_reachability`;
  - `ObservationService.start_wait`;
  - `WorldModel.look`, `keypoint_at`, `camera_pose`, `view_spec`, `objects`, `perception`;
  - `BodyPort` and `BodyOpHandle`, moved in from `robot/`;
  - `ManipExecutor` with `backend`, `name` and `health()`.
- `world/model.py` and `robot/body_client.py` now import these Protocols instead of defining their own.
- `tests/contract/test_protocols.py` keeps them aligned.

### 5.3 Fixes found by running the whole thing

- **Reachability leaked ids (`services/reachability.py`).** Without candidates, `check_reachability` fell back to any
  ground-truth instance of the type and returned its `object_id` as `not_seen_here`. The planner could learn that an
  unseen `alarm_clock_1` exists. Now, when nothing of the type is visible, in the last scan here, or in a hand, the
  answer is `not_found` with no id, whether or not an instance exists elsewhere (PLAN 6.4 step 2). The contract test
  pins it.
- **LiteBody lagged the sim clock (`robot/lite_body.py`).** It moved a fixed distance per tick. At clock speed 40 on
  a loaded event loop, the body fell behind the sim clock that every timeout uses: a long walk could end
  `timed_out` (the runtime agent saw it once at speed 40), and sim durations grew with load (request to pick: 72 s of
  sim time at speed 20). Walking,
  turning and gliding now integrate over the elapsed sim time, capped at 1 s. Request to pick is now 57-61 s, and
  request to delivered 84-91 s, at speeds 10, 20 and 40.
- **Two navigation tests were geometry-fragile.** They cancelled the walk after 4 s, which on house 38 lands on the
  `living_room_dining_table_1a` stand, so the robot correctly reported `at` that keypoint. They now stop the walk in a
  stretch of path that is more than 0.7 m from every keypoint.
- **System 1 wiring.**
  - `eval/system1_routes.py` and `eval/system1_load.py` imported a module that had moved; they now import
    `tests.kept.system1_live_check`.
  - The page now calls System 1's `set_vocabulary` with the session's `object_type` enum (PLAN 8.5: Jev's
    `TARGET_WORDS`).
- **An offline System 1 path.** On lite, the page had no head frames, so System 1's frame gate, `frame()` and
  `observe()` never ran offline. `world/frames.py LiteFrames` now draws a labelled schematic from the head camera's
  ground-truth detections (enabled by `frames: lite` in `config/profiles/lite.yaml`).
- **Page server flags.** `--planner`, `--system1` and `--speed` were added to `ui/server.py` (and `WL_PLANNER`), so
  the page runs offline without keys.

## 6. Known gaps (found while integrating; each has an owner in §7)

1. **H15 `fetch_search` fails on lite.**
   - Cause: `apple_1` is on `kitchen_counter_1b`, whose AABB is 1.84 m deep against the kitchen wall (probably an
     L-shaped counter whose box spans the corner). The apple sits 0.15 m from the wall. mapgen put every stand of the
     counter on the open side of the box, 2.1 m from the apple, so `check_reachability` says `too_far` with no
     suggestion and the planner gives up.
   - Fix (mapgen): cut stretches from the occupancy or mesh footprint, not the AABB.
   - K10 has the same root cause: `counter_2b` spans the stove.
2. **H15's user surface is an armchair** whose box top (0.91 m) is the backrest. The proposed override is
   `living_room_dining_table_1a` (`config/stack.yaml scenes:` plus `eval/scenes.yaml`). It is not set yet, because gap
   1 blocks that scenario anyway.
3. **The Isaac profiles see through the d435 mount** (about 48° down, sees 0.2-1.0 m ahead). Arrival scans on `sonic`
   will be nearly empty until P1 renders a head camera (§7.1).
4. **Object poses on Isaac are static** (scene_info) until P1 has `get_objects`. A knocked object stays where it was.
5. **Interim executors, labelled in every result:**
   - halt is a body `stop` request with a 30 ms reply budget, not the latch lane;
   - the scan turns the whole body in place (`turn_in_place`), not the waist;
   - `reach_stance` is a `go_to` with a tight tolerance, not `approach`.
6. **The G1 workspace is uncalibrated**: reach 0.20-0.55 m forward, `arm_reach_m` 0.65, object heights 0.55-1.20 m.
   Low or deep objects need repositions.
7. **Not built yet:**
   - `eval/stack_suite.py` (G1-G14);
   - the page's GR00T strip, `list_locations` panel and scan thumbnails;
   - a live-LLM run of the 17 scenarios on lite.

   No integrated run has used a real model yet.
8. **Naming:**
   - `groot_sonic` (the token route) is still the `groot` backend's executor name in `api/skills.py`. Owner decision 7
     replaces it with `groot_arms`. `api.results` already treats `groot_arms` as a target executor.
   - `tests/kept/system1_stub.py` is the stub PLAN calls `tests/system1_stub.py`.
