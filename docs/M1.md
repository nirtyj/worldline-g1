# M1: SONIC walks the Unitree G1 in a MolmoSpaces house (Isaac Sim 5.1)

Status: **M1 exit criteria E1-E7 met on the Brev box (2026-09-29).** The final code passed the full cycle 3 times out
of 3: `m1_up.sh` from cold, the drive test through `BodyClient` only, then `m1_down.sh`. Runs
`run-20260929-030938`, `-031420` and `-031832`. The runs before the last fixes are listed in §5.3, failures
included.

The stack has three processes. **P1** `wl-isaac` is Isaac Sim 5.1 / Isaac Lab 2.3.2 with the G1 in MolmoSpaces
house `procthor-train-38` and a Unitree DDS bridge. **P2** `wl-sonic` is the **unmodified** C++ `gear_sonic_deploy`
in `zmq_manager` mode, driven through its `planner` topic. **P3** `wl-body` is our robot API: `BodyClient`, a
SONIC planner mux, a turn servo, and A* + pure pursuit on the house occupancy grid. The robot moves only through
SONIC's joint targets. P1 writes the root pose once, at spawn (`root_writes` = 0 in every run).

Evidence: `outputs/m1/run-<ts>/` on the box (`/work/worldline-g1/outputs/m1/`), pulled to the laptop under
`worldline-g1/outputs/m1/` (git-ignored). `outputs/m1/runs_summary.json` has one row per run.

## 1. Should we use only SONIC, or do other controllers fit this use case?

**Recommendation: keep SONIC as the only controller in the product path. Keep the interfaces controller-agnostic
(they already are) so a second controller could be added later, but do not build one now.** Other G1 controllers
exist and some of them walk. None of them beats SONIC on what this project needs: our Isaac 5.1 stack, the real-robot
deploy, and GR00T manipulation on top. Reasons:

1. **It works here, measured.** The unmodified SONIC deploy walks the G1 through the house on P1 with 0 falls in
   9 integrated runs (about 30 min of standing, walking, turning, strafing, stopping and 27 go_to legs). The
   deploy agent's characterisation adds about 12 more minutes on P1 with 0 falls.
2. **It matches the GR00T route we planned.**
   - GR00T's `unitree_g1_sonic` embodiment outputs SONIC `motion_token` actions
     (`Isaac-GR00T/gr00t/configs/data/embodiment_configs.py:67-88`).
   - NVIDIA's G1 VLA workflow (collect teleop data, fine-tune N1.7, deploy) runs on SONIC
     (`GR00T-WholeBodyControl/README.md:38`).
   - SONIC is not the *only* way to run GR00T on a G1. GR00T also has a decoupled-WBC embodiment with a navigation
     command (`unitree_g1_full_body_with_waist_height_nav_cmd`, `embodiment_configs.py:115`), and NVIDIA's Isaac
     Lab Arena checkpoints use it. N1.6 loco-manip runs on the HOMIE v2 lower body and N1.7 static pick-and-place
     on AGILE.
   - The arena spike ran those checkpoints (`arena_spike/README.md`): 5 of 27 and 7 of 30 successes, in Isaac Sim 6
     / Isaac Lab 3 at RTF 0.19-0.26. That is no evidence that the WBC route is better.
3. **Real-robot parity.** It is the same binary and the same DDS contract as on the real G1 (`deploy.sh sim|real`).
   P1 imitates the real robot's low-level interface, so the whole P2/P3 stack transfers unchanged.

plus a ~290-line observation adapter (arena spike). But that reopens the owner's "no AGILE" decision.

## 2. Runbook (on the box)

```bash
# once per laptop session: sync the code (outputs/ and .venv/ are never overwritten)
../ludo_robotics_prep_g1/00_infra/sync_wl.sh push
../ludo_robotics_prep_g1/00_infra/ssh.sh
source /etc/profile.d/ludo.sh && cd /work/worldline-g1

# the whole M1 cycle with all evidence in one dir: m1_up -> drive test -> m1_down  (~4.3 min)
bash scripts/m1_e2e.sh --tp-camera                    # -> outputs/m1/run-<ts>/ ; exit 0 only if everything passed

# or step by step
bash scripts/m1_up.sh [--house procthor-train-38]     # tmux wl-m1: isaac, body, deploy, monitor; ~58 s to standing
.venv/bin/python -m tools.m1_drive_test --stand-s 60  # E2-E5 through BodyClient only
.venv/bin/python -m tools.body_cli walk --vx 0.5 --duration 4      # manual: stand|walk|turn_to|go_to|stop|status|p1 <op>
.venv/bin/python -m tools.body_cli go_to --x 4.1 --y 6.1 --yaw-deg 90
bash scripts/m1_down.sh                               # band on -> deploy stop -> body -> P1; ~6 s
bash scripts/m1_restart_body.sh                       # dev only: restart P3 on a running stack and re-adopt SONIC

# summarise runs (laptop or box)
python3 -m tools.m1_summarize outputs/m1/run-A outputs/m1/run-B ...
# pull evidence
../ludo_robotics_prep_g1/00_infra/sync_wl.sh pull /work/worldline-g1/outputs/m1/run-<ts>/ outputs/m1/run-<ts>
```

Options for `m1_up.sh` (env): `ISAAC_ARGS="--tp-camera"` (third-person camera), `NAV_BACKEND=astar|nav2`
(default `astar`; `nav2` starts `nav2/m1_hook.sh`, see `docs/nav2.md`), `DEPLOY_TASKSET=0-3 ISAAC_TASKSET=4-15
BODY_TASKSET=4-15` (the defaults; set them to `""` to disable pinning), `BODY_ARGS="--turn-push 0.6 ..."`.

Python API (`body/client.py`, contract §3.5):

```python
from body.client import BodyClient
bc = BodyClient().connect()
bc.stand(); bc.walk(vx=0.5, duration_s=4); bc.turn_to(math.pi / 2); bc.go_to(4.1, 6.1, yaw=math.pi / 2)
bc.stop(); bc.pose(); bc.status(); ts, rgb = bc.camera_frame()
h = bc.go_to(7.1, 2.2, wait=False); h.cancel()        # every motion returns an OpHandle; failures are reported, never faked
```

Rules: run the integrated stack on a **quiet box**. The deploy is wall-clock and contention-sensitive (§7). Only
one deploy + sim pair may run per network namespace, because DDS domain 0 is hard-coded in the deploy.
`m1_up.sh` refuses to start if the session or any contract port is already in use.

Start order (`scripts/m1_up.sh`): P1 (wait for `WL_ISAAC_READY`, gt.pose ≥ 40 Hz, lowstate, camera; band on at
floor + 0.80 m) → P3 (binds 5556 and streams planner IDLE before the deploy connects) → P2 (`run_deploy.sh start
--wait-init`: `Init Done` + `robot_config`) → `stand` (`command{start,planner}`, wait for `init_base_quat` in
g1_debug, 2 s IDLE, band release with a 1 s ramp, 3 s upright check) → monitor window. Stop order
(`scripts/m1_down.sh`): body `stop` (IDLE) → band on → `shutdown_control` (`command{stop}`: the deploy damps and
exits while the band holds the robot) → `run_deploy.sh stop` → body → P1 `shutdown` → kill only the `wl-m1` session.

CPU: P1 uses about 2.75 cores (pinned 4-15). The deploy's main thread busy-spins pinned to CPU 0 (pinned 0-3). P3
uses about 0.1 core. GPU: P1 3.3 GB and the deploy 1.3 GB (run A, `box_load_after.txt`).

## 4. Integration path (E6)

**Chosen: the Isaac-side Unitree DDS bridge on CPU PhysX at 200 Hz, paced to the wall clock, driven by the
unmodified wall-clock `gear_sonic_deploy`.** The SONIC-only fallbacks (in-process lockstep SONIC with
`planner_sonic.onnx`, or a sim-clock deploy patch) are **not needed for M1**. Reasons, all measured:

| Config (1 G1, house `procthor-train-38` unless noted) | RTF total | worst 1 s | 1 s windows < 0.95 | physics Hz | notes |
|---|---|---|---|---|---|
| P1 alone, head camera 30 Hz, CPU, paced (isaac agent, quiet box, train-40) | 0.998 | 0.878 | 1.8 % | 200.0 | free-running 1.294 = 29 % headroom (contract §1.10) |
| P1 alone, same, **GPU** PhysX | 0.220 | 0.203 | 100 % | 44 | rejected: PhysX step 19 ms for 1 robot |
| **Full M1 stack** (P1 + head cam 30 Hz + chase cam 10 Hz + deploy + body), final runs A/B/C | **0.994-0.995** | **0.824-0.826** | **2.4-3.2 %** | 192-196 (1 s) | 1.0-1.35 s of sim time lost per run to render hitches; 0 falls |
| Full stack without the chase camera (run-022923) | 0.995 | 0.714 | 3.0 % | 200.8 | the chase camera costs about +4 ms per render (13.5 vs 9.4 ms mean) and did not change RTF measurably |

Per sim second of wall time: 200 physics steps × 2.15 ms plus 30 renders × 13.5 ms ≈ 0.84 s. The rest is headroom.
SONIC is robust to the residual hitches: P1's lowstate heartbeat keeps the deploy's 500 ms staleness check from
firing, and the deploy's own 50 Hz loop never missed a tick (sonic_deploy.md §7). The lockstep fallback would buy
bit-exact timing but loses real-robot parity: a different process model, and the Python policy instead of the
TensorRT deploy. It stays the documented contingency for heavier scenes, several cameras or a busy box.

## 6. What the integration changed (on top of the build-phase components)

- **`scripts/m1_up.sh`**:
  - Every tmux window sources `/etc/profile.d/ludo.sh`. A tmux server that is already running gives new windows
    *its* environment, and without `OMNI_KIT_ACCEPT_EULA` Isaac blocked on the EULA prompt.
  - Default house `procthor-train-38`: kitchen 43.8 m², bedroom 36.5 m², living room 29.2 m², 5.4 m straight run at
    spawn (docs/scenes.md).
  - `NAV_BACKEND=astar` by default. The contract's A* PathFollower is what M1 tested; `nav2` is optional through
    `nav2/m1_hook.sh`.
  - Pinning defaults (deploy 0-3, Isaac and body 4-15).
  - P1 stats and artefacts go into the stack run dir, and the log paths are recorded there.
- **`body/motions.py` `FacingServo`** (turn_to and go_to's final turn). SONIC's IDLE + facing turn stops about 20 %
  short of the target. The servo pushes the command past the target by 0.6 × the residual once the robot has
  settled. It is the deploy agent's P1-measured fix: the committed logic reached the 6° tolerance on 0 of 5 turns,
  with the push on 5 of 5. Integrated: turn_to errors 0.3-4.1° in 3.9-8.0 s; go_to final heading errors ≤ 6.2°.
- **`WalkMotion`**:
  - The body frame is the *actual* GT heading at the start of the op.
  - Straight forward-dominant walks run pure pursuit on the start line: a 1.0 m lookahead, the same law as go_to.
    This took the lateral error from 0.29-0.55 m open loop to ≤ 0.024 m.
  - Strafes stay open loop. Their distance on P1 is set by SONIC's lateral stepping (§7, item 1): 0.27-1.11 m open loop
    for 0.3 m/s × 4 s. The line hold did not help (0.33-0.51 m in 4 runs).
- **`PlannerFrame` bias integrator off** (`heading_bias_ki` 0). P1's IMU is the GT pelvis orientation, so the frame
  from `g1_debug.init_base_quat` is exact. The only steady heading error is the planner's turn shortfall, which
  FacingServo handles.
- **go_to**: a separate `approach_tol` (0.12 m) triggers the slow approach, and `final_pos_tol` (0.25 m) stays the
  success bar. Before, a leg could stop at 0.21 m without an approach.
- **Drive test**:
  - The E4 verdict is a set of checks: lowcmd and leg-target rates, `g1_debug` rate, `SLOW_WALK` sent, deploy
    planner mode (from its log), planner target moving, contact alternation, no root writes, no `command{stop}`.
  - Strafe is 0.4 m/s × 5 s and needs 1.6 m of free space on the chosen side.
  - A thread-safe g1_debug recorder.
- New scripts: **`scripts/m1_e2e.sh`** (one full cycle with evidence), **`scripts/m1_restart_body.sh`** (dev),
  **`tools/m1_summarize.py`**.

Contract deviations are recorded in `docs/contracts/m1.md` (P1 §1, body §3.7) and `docs/contracts/sonic_deploy.md`.
The main ones:
- DDS domain 0 is hard-coded in the deploy.
- A user `stop` is planner IDLE; `command{stop}` terminates the deploy and is sent only at shutdown.
- `g1_debug` exists only in CONTROL.
- The body starts before the deploy.
- `rt/lowcmd` arrives at about 500 Hz with targets changing at 50 Hz ("lowcmd ~50 Hz" in E4).

## 7. Known issues and risks

1. **Lateral stepping gap on P1.** In SONIC strafes the robot realises only 40-85 % of the planner's own lateral
   target at 0.3 m/s. For 4 s, the planner `base_trans_target` moved 0.89-1.15 m and GT moved 0.38-0.88 m, and
   sometimes the robot stalls after 2 steps. At 0.4 m/s it realises 76-98 %. MuJoCo realises about 100 %
   (0.89-1.12 m, sonic_deploy.md §6). Forward walking tracks well. Likely causes are foot/floor contact or
   friction parity between P1 and training; this is not investigated. M2 manipulation approach moves should prefer
   forward walking plus turning.
2. **Speed with frequent re-plans.** Closed-loop walks (pure pursuit, go_to) re-plan SONIC whenever the direction
   changes by more than 2°. For the same 0.5 m/s × 6.2 s command they cover 25-40 % more distance than open-loop
   walks: 3.4-3.8 m against 2.6-2.7 m. This is harmless for M1, but speed is not a calibrated quantity.
3. **Render hitches.** `sim.render()` occasionally takes 70-170 ms, a few per minute, inside Kit/RTX. They cost
   1.0-1.35 s of sim time per 4-minute run (`lost_s`) and set the worst 1 s RTF window of about 0.82. SONIC
   walked through all of them.
4. **Contention.** The wall-clock deploy needs a quiet box: other Isaac/MuJoCo jobs lower the worst-window RTF
   (0.88 → 0.77 measured by the isaac agent) and made the MuJoCo reference fall. During the final runs A-C no
   other agent's job was among the top processes (`box_load_{before,after}.txt`). The earlier runs had the Nav2
   fakes (about 0.3 core) alongside.
5. **Stops take 1.0-1.2 s** from a 0.5 m/s walk (limit 1.5 s). SONIC glides for about 2 steps after IDLE.
6. **The chase camera** can clip into walls when the robot backs up to one (visible in the stand phase of
   `third_person.mp4`). It is evidence only.
7. **Only one house was tested integrated** (`procthor-train-38`). P1 and SONIC were also verified on
   `procthor-train-40` by the isaac agent (stand, walk, turn). `train-40`'s living room has only 1.3 m² of
   reachable floor.
8. `walk` has no obstacle check; it is a velocity primitive. `go_to` is the safe way to move in the house.
9. **Nav2 backend** (`nav2/`, `docs/nav2.md`) is optional and **not** tested with SONIC in the loop; only A* was
   used in M1.

## 8. What M2 needs

- **World model from P1 ground truth:** `get_scene_info` (rooms with polygons, 67-100 objects with category, room
  and AABB) plus `gt.pose` give Worldline's `where` / object queries directly (PLAN.md §6.2). Loose props are
  dynamic: read their live pose from PhysX (`ObjectInfo.body_path`, docs/scenes.md), not from the USD transform.
- **Navigation API = `BodyClient.go_to`** (± `yaw`), already failure-typed (`no_path`, `goal_in_obstacle`, `stuck`,
  `final_error`, `fallen`, `timeout`) and cancellable. Worldline's navigate tool should map onto it. The "near
  object" goal needs an approach-pose sampler on the occupancy grid (not built).
- **Observation:** `BodyClient.camera_frame()` gives the head camera (looks about 48° down, like the real d435). A
  forward-looking camera for the planner / VLM would be a P1 option (another render product, about +5 ms per
  render at 30 Hz: affordable with the measured headroom).
- **Manipulation (GR00T N1.7):** SONIC token streaming through the deploy's `pose` / VLA input (not the planner
  topic). The deploy is already the executor; the new part is a P3 streamer that alternates between planner
  locomotion and token execution (PLAN.md §7.4). Dex3 hand commands already flow through P1.
- **Scene variety:** run `scenes/run_house_test.sh <id>` once per new house to cache its occupancy and spawn.
- **Time budget:** the real-time budget has about 16 % headroom with 2 cameras. More cameras or heavier scenes may
  need the lockstep fallback (§4).
- **Worldline integration** (the M2 work itself) was deliberately not touched in M1.
