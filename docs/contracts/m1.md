### 1.1 Launch

```bash
source /etc/profile.d/ludo.sh && cd /work/worldline-g1
/work/envs/isaaclab/bin/python -m sim_isaac.app \
    --house <id|empty> --physics-hz 200 --dds-domain 0 --dds-iface lo \
    --camera 640x480 --camera-hz 30 [--rt-pace] [--physx-device cpu] \
    [--port-offset 0] [--spawn x,y,yaw] [--tp-camera] [--stats-out <json>] [--duration <s>] [--out-dir <dir>]
# or: bash sim_isaac/tools/run_app.sh <args>        (foreground)
#     bash sim_isaac/tools/bg_app.sh <name> <args>  (tmux isaac-app-<name>, waits for READY)
```

- Headless always; `--enable_cameras` is added automatically when `--camera` is not `none` or `--tp-camera`.
- `--rt-pace` is the default (`--no-rt-pace` free-runs, for measurements only). `--physx-device cpu` is the default
  and the measured choice (§1.10).
- Readiness: P1 prints one line `WL_ISAAC_READY {json}` (ports, house, spawn, floor_z, physx_device, ...) once
  lowstate is flowing and the band is **on**, then answers `ping`. The ZMQ server sockets are bound first, so a
  second instance on the same ports fails in about 1 s with `Address already in use`.
- The G1 USD is built once: `python -m sim_isaac.g1_asset --build` (writes `/work/worldline-g1/assets/g1/`).
- Start-up: ~15 s (empty) to ~25 s (house) including 30 camera warm-up renders and a cached top-down render.

### 1.2 Robot model (training parity)

- URDF: SONIC's training `gear_sonic/data/assets/robot_description/urdf/g1/main.urdf` with the 14 Dex3 hand joints
  switched from `fixed` to `revolute` (axis/limit/origin copied from
  `gear_sonic/data/robot_model/model_data/g1/g1_29dof_with_hand.urdf`; they are identical, checked), mesh paths made
  absolute, converted with Isaac Lab `UrdfConverter` (`fix_base=False`, `merge_fixed_joints=True`,
  `replace_cylinders_with_capsules=True`, drive gains 0), exactly the options of `robots/g1.py:199-222`.
  Result: 43 joints, 44 bodies.
- Actuators: the `actuators` dict of `G1_CYLINDER_MODEL_12_DEX_CFG` (`gear_sonic/envs/manager_env/robots/g1.py:238-357`),
  **imported** from gear_sonic, not copied: implicit PD, armature, `effort_limit_sim`, `velocity_limit_sim`. Dex3
  joints: an extra implicit group (armature 0.01 like the MuJoCo `finger_motor` class, `g1_29dof_with_hand.xml:20-22`;
  effort/velocity limits from the URDF; initial kp/kd 1.5/0.1 = the deploy's Dex3 hold, `dex3_hands.hpp:308-332`).
- Articulation root: self-collisions on, solver 8 position / 4 velocity iterations (`g1.py:214-218`); rigid props and
  `activate_contact_sensors=True` as in training.
- Physics: dt = 0.005 s (`base_env.yaml:32`; MuJoCo `SIMULATE_DT`), TGS, ground/house floor friction static =
  dynamic = 1.0 combine `multiply` (`modular_tracking_env_cfg.py:319-330`), `gpu_max_rigid_patch_count` as training.
- PD (`--pd implicit`, default): the lowcmd `kp`/`kd` are written into the PhysX drives (only when they change by
  more than 1%), `q`/`dq` become drive targets, `tau` is a feed-forward actuation force. The deploy's `kps`/`kds`
  equal the training stiffness/damping (`policy_parameters.hpp:143-208` vs `g1.py:15-26`): training parity.
  `--pd explicit`: `clip(tau + kp(q*-q) + kd(dq*-dq), ±effort_limit)` at 200 Hz like MuJoCo `base_sim.py:258-288,423`.
- Before the first `rt/lowcmd` the joints hold the default standing pose with the training gains (MuJoCo applies
  zero torque; deliberate deviation so the robot does not flop on the band). After that the latest lowcmd is applied
  every physics step and never timed out (MuJoCo semantics).
- A static PD stand with the training gains **cannot** balance (measured: falls 1.7 s after band release; ankle kp
  28.5 Nm/rad vs a toppling stiffness m·g·h ≈ 240 Nm/rad). Balance is SONIC's job; release the band only after the
  deploy is in CONTROL.

### 1.3 DDS (unitree_sdk2py + cyclonedds 0.10.2, `unitree_hg` IDL, same types as the real G1 and the MuJoCo bridge)

P1 mirrors `gear_sonic/utils/mujoco_sim/unitree_sdk2py_bridge.py` + `base_sim.py`:

P1 is **controller-agnostic by construction**: it exposes the real G1's low-level Unitree DDS interface (`rt/lowcmd`
in; `rt/lowstate` + `rt/secondary_imu` + Dex3 out) and nothing SONIC-specific. Any controller that drives a real G1
through unitree_sdk2 low-level mode can drive P1 unchanged; e.g. the Decoupled WBC (GR00T N1.5/N1.6) in the same
repo publishes `rt/lowcmd` with the same SDK (`decoupled_wbc/control/envs/g1/utils/command_sender.py:45`). Swapping
the controller is a P2 (+ P3 command adapter) change only; P1 is untouched.

| Topic | Dir | Type | Content |
|---|---|---|---|
| `rt/lowstate` | PUB, every physics step (200 Hz) | `LowState_` | `motor_state[0..28].{q,dq,ddq,tau_est}` in Unitree motor order; `imu_state.quaternion` = pelvis orientation **wxyz** in world; `gyroscope` = pelvis angular velocity in the **pelvis frame**; `accelerometer` = pelvis linear acceleration in the **world frame without gravity** (MuJoCo `qacc[:3]`, bridge `:185-194`); `tick = int(t_sim·1000)` (`:202`); `mode_machine` = `--mode-machine` (default 0: the MuJoCo bridge never sets it); `crc` = the SDK CRC (`--crc`, default on; the deploy in sim runs `--disable-crc-check` anyway, `deploy.sh:405`). `tau_est` = clipped PD torque estimate |
| `rt/secondary_imu` | PUB, 200 Hz | `IMUState_` | `quaternion` = torso_link orientation wxyz in world; `gyroscope` = torso_link angular velocity in the **torso frame** (bridge `:196-197`, `base_sim.py:359-371`). The deploy refuses to run without it |
| `rt/odostate` | PUB, 200 Hz | `OdoState_` | `position`, `linear_velocity` (world, pelvis origin), `orientation` (**wxyz**, as the MuJoCo bridge writes it despite the IDL comment), `angular_velocity` (pelvis frame) |
| `rt/dex3/{left,right}/state` | PUB, 200 Hz | `HandState_` | `motor_state[0..6].{q,dq}` in Dex3 order |
| `rt/lowcmd` | SUB | `LowCmd_` | `motor_cmd[0..28].{q,dq,kp,kd,tau}`; the newest sample is taken every physics step |
| `rt/dex3/{left,right}/cmd` | SUB | `HandCmd_` | `motor_cmd[0..6].{q,dq,kp,kd,tau}`; newest sample every 4th physics step (50 Hz) |

Motor order (hardware = MuJoCo order, `robot_parameters.hpp:90-130`, `g1_29dof_sonic_model12.yaml:119-148`):
legs 0-11 (`left_hip_pitch, left_hip_roll, left_hip_yaw, left_knee, left_ankle_pitch, left_ankle_roll`, then right),
waist 12-14 (`yaw, roll, pitch`), left arm 15-21 (`shoulder_pitch, shoulder_roll, shoulder_yaw, elbow, wrist_roll,
wrist_pitch, wrist_yaw`), right arm 22-28. Dex3 order per hand (MJCF order used by the MuJoCo bridge,
`base_sim.py:228-240`): `thumb_0, thumb_1, thumb_2, middle_0, middle_1, index_0, index_1`. Isaac joints are mapped
**by name** (joint-map test: every motor moves the named Isaac joint, §1.9).

Implementation (mechanics only, content unchanged): a fixed-layout CDR codec (`sim_isaac/fastdds.py`) replaces
cyclonedds-python's pure-Python (de)serializer (~3 ms/step). Every codec is checked at start-up against the library
byte-for-byte (writers, incl. the LowState CRC over the C struct layout) or value-for-value (readers); the check
result is logged as `codec_verified={...}` and a failed check falls back to the library path. Readers use the SDK's
default QoS (KEEP_LAST 1) and are polled once per physics step instead of a listener thread per sample (the MuJoCo
bridge also only uses the newest command, `queueLen=1`).

Lowstate heartbeat: if physics publishes no lowstate for `--heartbeat-ms` (default 50 ms, e.g. a render hitch), a
thread re-publishes the last `rt/lowstate` + `rt/secondary_imu` so the deploy's 500 ms `LOW_STATE_ABSENT_THRESHOLD`
(`g1_deploy_onnx_ref.cpp:299,2797-2812`) never fires on a hitch. Counted in `get_stats.heartbeat_pubs`.

The cyclonedds 0.10.2 C library on the box is built with `-D_FORTIFY_SOURCE=0` (`/work/opt/cyclonedds-0.10.2`):
with Ubuntu 24.04's default fortify level, creating a domain with a network interface aborts with
`*** buffer overflow detected ***`. Anyone running unitree_sdk2py in `/work/envs/isaaclab` gets this build.

### 1.4 Camera (PUB 5565, gear_sonic sensor_server format)

- Mount: a child prim of `torso_link` at the `d435_link` offset `xyz=(0.0576235, 0.01753, 0.41987)`,
  `rpy=(0, 0.8307767, 0)` (`g1_29dof_with_hand.urdf:614-619`; `main.urdf` has no `d435_link`). It looks ~48° down,
  so it mostly sees the floor and the hands in front of the robot, like the real head camera.
- 640x480 pinhole, vertical FOV 45° (MuJoCo `head_camera` default `fovy`), square pixels (HFOV 57.8°), clipping
  0.05-50 m, rendered every 1/30 s of **sim time** (`IMAGE_DT = 0.0333`, `base_sim.py:70`).
- Wire format, byte-compatible with `gear_sonic/utils/mujoco_sim/image_publish_utils.py:165-185` +
  `sensor_server.py:57-77`: one ZMQ frame = `msgpack.packb(d, use_bin_type=True)` with
  `d = {"timestamps": {"ego_view": <wall time.time()>}, "images": {"ego_view": <b64 str>}, "ego_view": <b64 str>,
  "t_sim": float, "seq": int}`, `<b64 str>` = `base64(cv2.imencode(".jpg", rgb, [IMWRITE_JPEG_QUALITY, 80]))`.
  As in MuJoCo, the RGB array goes to `cv2.imencode` unchanged, so `ImageUtils.decode_image` returns **RGB**.
  `t_sim`/`seq` are extras that gear_sonic consumers ignore. Encoding runs on a worker thread; SNDHWM 20.

### 1.5 PUB 5601 (ground truth stream)

Multipart `[topic, msgpack(payload)]`. Subscribe with `setsockopt(zmq.SUBSCRIBE, b"gt.pose")` (no CONFLATE).

`gt.pose` at 50 Hz of sim time (every 4th physics step):

```
{ "seq": int, "t_sim": float, "t_wall": float, "rtf": float|null,   # rtf over the last ~1 s
  "base_pos": [x,y,z],            # pelvis origin, world, m
  "base_quat_wxyz": [w,x,y,z],    # pelvis orientation, world
  "base_lin_vel_w": [vx,vy,vz],   # pelvis origin velocity, world frame
  "base_ang_vel_w": [wx,wy,wz],   # world frame
  "yaw": float,                   # rad, CCW from world +x, in (-pi, pi]
  "pelvis_z": float,              # base_pos[2] - floor_z (standing: ~0.75)
  "fallen": bool,                 # pelvis_z < 0.45 m or pelvis up-axis tilt > 60 deg
  "foot_contact": {"left": bool, "right": bool},   # ankle_roll_link net contact force > 20 N
  "band": bool,                   # elastic band engaged
  "lowcmd_age_s": float|null      # seconds since the last fresh rt/lowcmd (null = never)
}
```

`gt.event` (sporadic): `{"t_sim", "t_wall", "event": "band"|"reset_robot"|"fallen"|"recovered", ...}`.

### 1.7 Elastic band

Port of `ElasticBand` (`unitree_sdk2py_bridge.py:366-395`): a world-frame wrench on the pelvis every physics step,
force `kp_pos·(anchor − pos) − kd_pos·vel` (`kp_pos = 10000, kd_pos = 1000`), torque `−kp_ang·rotvec − kd_ang·ω`
(`kp_ang = 1000, kd_ang = 10`). Differences from MuJoCo: the anchor is `(x, y)` of the pelvis at engage time and
`floor_z + z` (default 0.80 m: feet just on the floor, pelvis ~0.77 m), and the orientation target is upright with
the **yaw at engage time** (MuJoCo drives to yaw 0). `ramp_s > 0` scales the gains to zero linearly in sim time.

### 1.8 Scene plugin (house agent) and extra frames

`--house <id>` calls `scenes/loader.py: load_house(stage, house_id[, dynamic_objects=...]) -> HouseInfo` after the
physics scene exists and before the robot spawns (no InteractiveScene). P1 reads `house_id`, `floor_z`, `spawn`,
`bounds`, `rooms`, `objects`, `occupancy_npz`, `to_scene_info()`; the spawn defaults to `HouseInfo.spawn`
(`--spawn x,y,yaw` overrides). Default lights (dome + distant) are added. `--house empty`: 30 m × 30 m ground plane.

`--tp-camera` (optional, costs a second render product per render, ~+7 ms/render): a third-person chase camera on
PUB 5602, multipart `[b"frame.tp", msgpack{seq, t_sim, t_wall, jpeg (bytes; decodes to RGB), base_pos, yaw}]` at
`--tp-hz` (10). `sim_isaac/tools/record_video.py --ego --tp --topdown` writes `ego.mp4`, `tp.mp4` and a zero-cost
`topdown.mp4` (gt.pose drawn over the cached top-down render).

**Decision: the primary path.** P1 runs the Isaac-side Unitree DDS bridge on **CPU PhysX at 200 Hz with wall-clock
pacing**, and the **unmodified** C++ `gear_sonic_deploy` (zmq_manager, planner topic) drives it on its own wall
clock, exactly as it drives the MuJoCo sim and the real robot. Reasons:
1. Measured RTF with 1 G1 + house + head camera at 30 Hz is 0.998 total and 1.000 over 10 s windows, with ~30%
   free-running headroom; with the deploy in the loop 0.993 / 1.000.
2. The unmodified deploy stands (60 s), walks (2.5 m), stops and turns the G1 in the MolmoSpaces house through
   P1 with joint-level control only (§1.9); no root writes after spawn.
3. GPU PhysX is rejected: for one robot its pipeline overhead makes the PhysX step 4× (bare) to 17× (house) slower
   than CPU PhysX (RTF 0.95 bare, 0.22 in the house).
4. The SONIC fallbacks (a) in-process lockstep SONIC and (b) a sim-clock deploy patch are therefore **not needed for
   M1**. They stay the documented contingency if RTF drops (e.g. several cameras, a heavier house, a busy box).

Residual risks (known issues):
- **Render hitches.** `sim.render()` occasionally takes 70-190 ms (a few per minute, cause inside Kit/RTX; not
  Python GC: `gc.freeze()` after start-up leaves only gen-0 collections of ≤ 0.1 ms in the loop). The pacer drops
  lag beyond 100 ms (`overruns`, `lost_s` in `get_stats`: 0.1-0.5 s per minute); the lowstate heartbeat thread keeps
  `rt/lowstate` flowing (`heartbeat_pubs`: 2-9 per run), so the deploy's 500 ms `LOW_STATE_ABSENT_THRESHOLD`
  never fires. SONIC walked through them in every run.
- **CPU contention.** P1 uses ~2.8 cores (`process_cpu_pct` 280%) and the deploy is wall-clock sensitive: other jobs
  on the box lower the worst 1 s RTF (0.88 → 0.77) and made the deploy agent's MuJoCo reference fall. Run the
  integrated stack on a quiet box; `ISAAC_TASKSET` / `DEPLOY_TASKSET` pinning is available in `m1_up.sh`.
- The contract's `rtf` in `gt.pose` (1 s window) and `get_stats` (`rtf_*`, `overruns`, `lost_s`, `hitches_gt25ms`,
  `gc`) let P3 and the drive test record the RTF actually achieved in every run (E5).

### 3.2 SONIC input (P3 → P2, PUB 5556): SonicMux

- Wire: `[topic][1280-byte null-padded JSON header][LE payload]`, one frame. `body/wire.py` is a verbatim port of
  `gear_sonic/utils/teleop/zmq/zmq_planner_sender.py:14-158`; `body/tests/test_wire.py` asserts **byte equality**
  with the upstream module. Receiver rules: `zmq_packed_message_subscriber.hpp:99, 272-329`, `zmq_manager.hpp:668-800`.
- `command`: `{start:u8, stop:u8, planner:u8}`. The body sends `start=1, stop=0, planner=1` (3×) on `stand` only.
  `stop=1` is sent **only** by the `shutdown_control` op (m1_down.sh, band on first): it makes the deploy run
  `Stop()` → `CreateDampingCommand()` (kp=0, kd=8) and exit (`g1_deploy_onnx_ref.cpp:2718-2745, 4513-4530`).
  A user `stop` is planner IDLE, never `command{stop}`.
- `planner`: `mode:i32, movement:f32[3], facing:f32[3], speed:f32, height:f32(-1)`, re-sent at **50 Hz** (≥10 Hz
  needed: 1 s timeout to IDLE, `zmq_manager.hpp:581-642`) from bind until exit, IDLE `movement=[0,0,0]` when no
  motion runs. Directions within 2° and speeds within 0.03 m/s of the last sent message reuse the exact previous
  f32 values, so noise does not force deploy re-plans (`g1_deploy_onnx_ref.cpp:3659-3732`).
- Modes used: 0 IDLE (stand, stop, turn in place with a new `facing`, as keyboard Q/E do,
  `keyboard_handler.hpp:556-566`), 1 SLOW_WALK with `speed` clamped to 0.2–0.8 m/s (`keyboard_handler.hpp:267-272`),
  ≤0.4 m/s when the motion is mostly sideways (`docs/source/tutorials/keyboard.md` strafe tip). WALK/RUN unused.
- **Planner frame.** `movement`/`facing` are in the planner frame whose +x is the pelvis heading when the planner
  was initialised (`localmotion_kplanner.hpp:591-624`; policy mapping `g1_deploy_onnx_ref.cpp:560-606`). The body
  converts world directions with `R(-(θ0 + δ - b))`, where `θ0 = yaw(init_base_quat)`, `δ = delta_heading`, both read
  from `g1_debug` (`zmq_output_handler.hpp:43-45`); until the first `g1_debug` arrives, `θ0` = GT yaw captured when
  `start` is sent. `b` is a slow integral of the GT heading error, learned only while IDLE, settled and with an
  unchanged facing for > 1.5 s (clamped to ±20°).
- Watchdog in the mux: if the 50 Hz control loop has not refreshed a non-IDLE command for 0.3 s, the mux sends IDLE
  with the last facing instead of repeating the stale walk.

### 3.4 Control API: ROUTER 5610 / PUB 5611

Request (DEALER or REQ, one JSON frame): `{"id": str (optional, echoed), "op": str, "args": {...}}`.
Reply: `{"id", "ok": bool, "state": "accepted"|"rejected"|"failed"|"done", "error"?: str, "data"?: {...}}`.
Motion ops reply after `start()` has run, so bad args / no path / not standing come back synchronously. Exception:
go_to with the `nav2` backend waits at most 45 ms for the bridge's goal check + plan (typically 10-20 ms); a later
answer arrives as the terminal event after `accepted` (same reasons).

Events: multipart `[b"body.event", JSON]`:
`{"id", "op", "state": "accepted"|"progress"|"succeeded"|"failed"|"canceled", "data": {...}, "seq", "t_wall"}`.
Every op gets exactly one terminal event (a rejection also publishes `failed` with `data.reason`).
State: multipart `[b"body.state", JSON]` at 5 Hz: `in_control, control_started, fault, active {id, op, phase},
pose, gt_pose {rate_hz, age_s, rtf}, deploy {alive, rate_hz, in_control, legs}, mux {rate_hz, stats, frame,
last_sent}, nav, tick`. The first `body.state` a client sees proves its SUB is live.

| op | args (defaults) | terminal `data` (besides `final_pose`, `start_pose`, `displacement_m`, `displacement_body0`, `yaw_change_deg`, `walked_m`, `duration_s`) |
|---|---|---|
| `stand` | `release_band` (true), `band_ramp_s` (1.0), `settle_s` (2.0), `verify_s` (3.0), `min_deploy_age_s` (4.0), `deploy_wait_s` (20) | `band_released, started_here, pelvis_z_min/max, frame`. Waits for the deploy (`robot_config`), sends `start`, waits for `init_base_quat`, holds IDLE, releases the band, checks pelvis_z in [0.55, 1.0] |
| `walk` | `vx, vy` (m/s, body frame at op start), `yaw_rate` (rad/s), `duration_s` (3.0, wall clock) | `speed_cmd, stop_time_s`. speed < 0.05 ⇒ pure turn. Heading at start rotates with `yaw_rate·t`; stops and settles after `duration_s` |
| `turn_to` | `yaw` (rad, world) or `yaw_deg`, `relative` (false), `tol_deg` (6) | `target_deg, yaw_err_deg`. Facing at most 90° ahead of the current yaw (unambiguous direction) |
| `go_to` | `x, y` (world), `yaw` or `yaw_deg` (optional), `speed` (0.45), `timeout_s` (180), `pos_tol` (0.15), `final_pos_tol` (0.25), `final_yaw_tol_deg` (12), `backend` (`nav2`\|`astar`, default `NAV_BACKEND`); nav2 only: `max_reapproach` (1), `max_escapes` (2), `max_nav_retries` (1) | `goal, pos_err, yaw_err_deg, path_len_m, replans, approach_attempts, stuck_events, plans[]` (each plan: `path` ≤60 pts, `length_m`, `plan_ms`, `goal_snapped`), plus `backend` (the one that ran); astar results also carry `backend_requested`, and `backend_fallback` (why nav2 was not used) after a fallback. nav2 adds `goal_requested, nav2 {state, reason, error_code, error_name, cmd_vel_forwarded, feedback}, nav2_recoveries, nav2_retries, escapes[], velocity {...}, goto_reply_ms[]` |
| `velocity` | `vx, vy` (m/s, body frame: x forward, y left), `wz` (rad/s), `stream` (str), `t_wall` (sender `time.time()`, optional), `watchdog_s` (0.3), `max_duration_s` (3600), `end` (bool) | `ended_by` (`watchdog`\|`client`), `stream`, `velocity {updates, stale_dropped, watchdog_trips, idle_steps, ...}`, `stop_time_s`. **Streaming op**, see below |
| `stop` | – | `stopped, stop_time_s, v_final` (IDLE, facing = current yaw; succeeds when speed < 0.05 m/s) |
| `status` | `id` (optional: that op's record) | the `body.state` dict (+ `op`) |
| `ping`, `reload_map`, `clear_fault` | – | – |
| `shutdown_control` | `confirm: true` (required) | IDLE 0.5 s then `command{stop}` ×3: **the deploy exits**. Band first |

Rules: one motion at a time; a new motion (or `stop`) cancels the active one, which ends `canceled` with
`data.reason = "preempted"` (+ `by`) or `"stop"`. Motion ops other than `stand`/`stop` need the deploy in CONTROL
(`not_standing` otherwise). Failure reasons: `not_standing, no_pose, pose_stale, deploy_stale, deploy_not_running,
deploy_not_ready, deploy_not_in_control, band_release_failed, pelvis_out_of_band, fallen, timeout, no_path,
goal_in_obstacle, start_in_obstacle, stuck, off_path, final_error, no_occupancy, bad_args, fault:fallen`; go_to with
the `nav2` backend also: `nav2_unavailable` (bridge unreachable at start, no goto reply within 8 s, or no status
reply for 3 s mid-goal), `nav2_rejected` (Nav2 refused the goal), `nav2_canceled` (the Nav2 goal was canceled by
someone else), `nav2_failed` / `nav2_aborted` (Nav2 failed without a mapped error code), `nav2_config` (invalid
planner / controller), `tf_error`; `velocity` also `stale_command` (first message older than `watchdog_s`). Both go_to
backends give the same reason for the same goal: a goal the robot centre cannot occupy is snapped to the nearest free
cell within 0.5 m, else `goal_in_obstacle` (also outside the map); a free goal that cannot be reached is `no_path`.

**`velocity` (streaming).** The first message starts the op (normal `accepted` event, pre-empts the active motion).
Every later message **must carry the same `stream`** (default: the op id, i.e. `data.stream` of the accepted reply):
it then only updates the twist, replies `state: "done"`, publishes **no event** and creates no op record. A message
without a matching `stream` starts a **new** op (and cancels the old one). `end: true` stops the stream. Messages
whose `t_wall` is older than `watchdog_s` are dropped. No fresh message for `watchdog_s` ⇒ planner IDLE (holding the
last commanded facing); the op ends `succeeded, ended_by: "watchdog"` once settled (a stream that resumes before
that continues the op). Conversion: `|v| < 0.05` ⇒ no translation, else SLOW_WALK in direction `R(yaw_gt)·(vx, vy)`
at clamp(|v|, 0.2, 0.8) (≤ 0.4 strafing); `wz` is integrated into a facing that SONIC gets in steps like `turn_to`:
≤ 30° from the last commanded facing, only while the body is within 15° of it, and in place (IDLE) at most one step
per 0.4 s. Messages with `args.goal_id` are Nav2's `/cmd_vel` from `nav2/ros_bridge.py`: they only feed the active
go_to with that id, never start an op; otherwise they are rejected with `error: "stale_goal"` (no event).
A fall (`gt.pose.fallen` or pelvis_z < 0.55 m after start) fails the active op, holds IDLE and latches
`fault="fallen"`; after a P1 `reset_robot`, send `clear_fault` (and `stand` again if needed).

go_to backends: **`nav2` (default)**: ROS 2 Nav2 through `nav2/ros_bridge.py` (Smac 2D planner, Regulated Pure
Pursuit, humanoid behaviour tree; docs/nav2.md). Before each go_to the body pings the bridge (≤ 50 ms; "unreachable" is
cached 3 s) and falls back to `astar` when it does not answer or Nav2 is not active (`backend_fallback` says why). All
bridge calls are asynchronous, so the 50 Hz loop never waits on ROS. Result semantics under nav2: `replans` = goal
re-sends by the body (escape steps, retries, re-approaches; Nav2's own 1 Hz replanning is not counted),
`stuck_events` = Nav2 `stuck` failures (`FAILED_TO_MAKE_PROGRESS`, `PATIENCE_EXCEEDED`, `NO_VALID_CONTROL`) with the
body's reaction (`escape`, `escape+retry`, `retry`, `none`), `nav2_recoveries` = Nav2 BT recoveries. A stuck goal is
re-sent once (`max_nav_retries`), after a slow ≤ 0.6 m escape step when the clearance is below the inflation radius
(0.45 m); a start inside the inscribed zone (< 0.30 m) gets an escape step first (≤ 2 per go_to).

**`astar`** (fallback) algorithm: A* (8-connected, octile, clearance-weighted cost `1 + 2·exp(-(clearance - r)/0.25)`) on a 0.10 m
grid sampled from the 0.05 m inflated grid, greedy line-of-sight shortcutting on the fine grid, 0.10 m resampling;
pure pursuit (lookahead 0.6 m, facing = direction of travel, speed `min(v, sqrt(2·0.35·d)+0.05)` ≥ 0.2); turn in place
first when the heading error > 50–70°; arrival 0.15 m → IDLE settle → up to 2 slow holonomic corrections → optional
final turn → check. Stuck = commanded motion but < 0.08 m progress in 3 s → IDLE, virtual 0.25 m obstacle ahead,
re-plan (max 2); cross-track > 0.6 m → re-plan.

### 3.7 Deviations from the baseline contract (body)

1. The body starts **before** the deploy (baseline: deploy then body), so the SONIC input PUB exists when the
   deploy connects (slow joiner) and the IDLE keepalive is already flowing (`sonic_deploy.md` §3 step 3).
2. `stop` never sends `command{stop}`; that is only `shutdown_control` (m1_down.sh, after band on). The baseline's
   "safe stop (mode idle then command stop)" is kept for shutdown only.
3. Health check "wait for g1_debug before start" is impossible: `g1_debug` exists only in CONTROL. m1_up waits for
   `Init Done` + `robot_config` instead; `stand` waits for `init_base_quat` in `g1_debug`.
4. Events use `canceled` (one l) as in the baseline; PLAN.md's envelope vocabulary uses `cancelled`.

### 3.8 Integration changes (M1, 2026-09-29; measured in `docs/M1.md` §5-§6)

1. `turn_to` and go_to's `final_turn` use `FacingServo` (`body/motions.py`): IDLE + facing (≤ 90° ahead, ≤ 30°
   steps), and once settled (|GT yaw rate| < 0.08 rad/s for 0.5 s) the command moves past the target by
   0.6 × the residual (`--turn-push`). This handles SONIC's ~20 % IDLE-turn shortfall (sonic_deploy.md §0.5).
   Default op timeout 25 s. Result `data.servo = {offset_deg, pushes}`.
2. `walk`: the body frame is the GT heading at op start (not the last commanded facing). Straight walks with
   |vx| ≥ |vy| and `yaw_rate` 0 hold the start line with pure pursuit (lookahead 1.0 m, correction ≤ 30°;
   `args.hold_line` false disables it). Strafes and curves stay open loop. Result adds `line_hold`,
   `max_cross_track_m`.
3. The planner-frame bias integrator is off by default (`heading_bias_ki` 0, `--heading-bias-ki`): on P1 the frame
   from `g1_debug.init_base_quat` is the GT frame.
4. `go_to`: `approach_tol` (0.12 m) triggers the slow approach after the settle; `final_pos_tol` (0.25 m) remains the
