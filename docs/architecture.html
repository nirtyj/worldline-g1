Worldline G1 Architecture

The whole loop: the Worldline runtime plans and watches, calls the robot API, and P3, the robot, turns those skills into commands for SONIC, which balances and walks a simulated Unitree G1 through a ProcTHOR house in Isaac Sim. GR00T N1.7 moves the arms from a second GPU box.

Revision r13 Updated 2026-09-29 Milestone M1 verified · M2b: navigation live, manipulation in test Boxes main ludo-g1-brev2 · dev ludo-g1-arena · 1× L40S each

At a glance

Four machines take part. The main box runs four processes that talk only over sockets: P1 wraps Isaac Sim and plays the G1's hardware, P2 is NVIDIA's unmodified SONIC controller, P3 is the robot, whose API merges leg and arm commands into one 50 Hz message to SONIC, and P5 is the Worldline runtime. In P5, System 2 plans one tool call at a time with Gemini 3.8 Flash, System 1 labels chat with TypeSafe Jev and watches gated head-camera frames through Gemini Live, and the world model is the only reader of simulator ground truth. The GR00T PolicyServer (P4) runs on the dev box and sends 0.8 s arm chunks back through groot-link, the OD3 SSH tunnel, into P3's arm channel. The laptop opens two browser tabs, the Sim Viewer :8765 and the Worldline UI :8766, through another SSH tunnel, and can also run the Stand-in UI :8777, which uses the cloud APIs but no simulator. Today the robot-side skills code still runs inside P5; per PLAN §0.14 it moves into P3 next, so Worldline will see only the robot API.

P3 robot API

P3 (body.service) binds three sockets: ROUTER :5610 for ops, PULL :5612 for the halt lane, and PUB :5611 for events. A reply is {id, ok, state: accepted | rejected | failed | done, error?, data?}, and every op ends with exactly one terminal body.event. Fences: each gated op carries execution_id, generation, control_epoch and session; an older one is refused as stale_command. Leases (LOCOMOTION, ARM_STREAM, ARM_SCRIPT, MANIP) give one owner per resource. Sessions (hello, ping at 4 Hz, bye; watchdog 1 s) let P3 halt the robot itself when the runtime disappears.

Halt lane · PULL :5612

PUSH {op: "halt", epoch, t_wall, reason} or {op: "resume", epoch}, fire and forget. On a halt P3 sends SONIC an IDLE at the current heading at once, latches the arms (hold the measured pose, hands never open), latches the fences, then acks with body.halted on :5611. It never sends command{stop}. Budget 30 ms; body handling ~0.1 ms, client receipt p50 ~0.6 ms; Worldline halt() p50 0.82 ms, max 1.77 ms over 20/20 live halts. Worldline re-sends an unacked halt every 100 ms.

Each planner step is one Gemini call that returns one tool call, and the validator checks it before the robot sees it. A "stop" typed at any point goes to P3's halt lane first (1-2 ms), before the planner hears about it. Navigation

A classic stack on top of SONIC walking. No learned navigation model; GR00T is used only for the arms.

  1. Place. Worldline's navigate(location) resolves a named place through the semantic map to a stand pose (today in P5's navigation service; in P3 after the §0.14 move).
  2. Map. The ProcTHOR house becomes a 5 cm occupancy grid (obstacles 0.1–1.6 m high, inflated by the G1 footprint), fetched from P1 get_occupancy.
  3. Pose. Isaac ground truth, gt.pose at 50 Hz; an op fails pose_stale after 0.5 s without it. The later no-ground-truth stage swaps in odometry.
  4. Plan and follow. A* on the grid, then pure pursuit turns the next path point into a SONIC walk command (direction, facing, 0.2–0.8 m/s) at 50 Hz; turn in place on a large heading error; arrival and stuck detection.
  5. Arrive. A waist scan (yaw −35/0/+35°) looks around; check_reachability may ask for approach, which repositions to about 1.5 cm.
  6. Step. SONIC's planner and policy do the legs and balance. Navigation never touches joints.

Nav2 stays in the tree behind :5620 and is deferred (PLAN §0.8); m1_up.sh defaults NAV_BACKEND to astar and m2_up.sh forces it.

Start-up and stopping

scripts/m2_up.sh --profile full --p5-port 8766, in this order; each stage waits on a readiness probe.

  1. GR00T link. groot_link.sh ensure: the dev-box PolicyServer must answer through the OD3 tunnel, or m2_up.sh exits 3 before anything starts.
  2. P1. Isaac starts with the robot held by the elastic band and prints WL_ISAAC_READY once lowstate flows.
  3. P3 body. Binds :5556 before the deploy connects to it.
  4. P2 deploy. Connects to lowstate and waits (Init Done after 32-36 s; the first start builds TensorRT engines, about 2 min).
  5. Stand. command{start}, planner IDLE, the band releases over 1 s, and the pelvis must stay at 0.55–1.0 m.
  6. P5. m2_p5.sh starts ui.server; ready when / answers and the WebSocket sends init. Then the GR00T link is checked again.

Stopping: m2_down.sh stops P5 first while the body holds, then the M1 stack. Shutdown re-engages the band, then sends command{stop}, which makes the deploy damp and exit.

Hard constraints

Wall clock. SONIC runs on the wall clock, so Isaac must keep up with real time (RTF p10 ≥ 0.98 is the gate). The POC stays on the wall clock (PLAN §0.13). If the gate fails even with GR00T on the dev box, the fallback is a --sim-clock scheduling patch to the deploy (lockstep with P1; policy and planner code unchanged).

Never command{stop} for a user stop. It collapses the robot and the deploy exits; only a restart recovers. A stop is planner IDLE; a halt also latches the arms.

A quiet GPU and CPU for the controller. The deploy is pinned to cores 0-3 and everything else to 4-15. Contention from other Isaac jobs caused the M1 falls, and GR00T on the same GPU broke the timing (§0.12), so GR00T runs on the dev box. Runs with degraded timing are marked invalid, not failed.

One sender to SONIC. SonicMux is the only binder of :5556. Legs from the Drive layer and arms from the Arm channel ride in the same 50 Hz planner message: GR00T's chunks become the optional upper_body_position/velocity (17) and Dex3 hand (7 + 7) fields, alongside whatever the legs are doing. Nothing takes turns, and the pose token topic is never sent.

Ground truth stays in the world model. Only world/ reads P1's ground-truth ports (a lint test enforces it); the planner sees belief only, and camera streams and g1_debug count as sensors.
