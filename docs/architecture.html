Worldline G1 Architecture

How GEAR-SONIC, Isaac Sim, the ProcTHOR house and our drive API fit together to make a simulated Unitree G1 walk through a home, and where Worldline and GR00T plug in next.

Revision r1 Updated 2026-09-28 Milestone M1 · SONIC G1 walking in a house Box Brev ludo-g1-brev2 · 1× L40S

At a glance

Everything runs on one GPU box as three processes that talk only over sockets, the way they would on a real robot. Isaac Sim simulates the G1 and a ProcTHOR house, and pretends to be the robot's hardware. SONIC, NVIDIA's whole-body controller, is the unmodified C++ binary a real G1 runs; it turns "walk this way" into 29 joint commands 50 times a second. wl-body is ours: it plans paths through the house and exposes the drive API (stand, walk, go_to, turn_to, stop). The simulator's ground truth (poses, rooms, objects, occupancy) is available to the robot layer, the same way ProcTHOR's metadata was on AI2-THOR.

Components

P1 · wl-isaac

sim_isaac/ · /work/envs/isaaclab (py3.11)
  • Isaac Sim 5.1 standalone app, headless, 200 Hz physics (CPU PhysX)
  • G1 from SONIC's training URDF with Dex3 hands made revolute, actuator parity with training
  • DDS bridge: publishes rt/lowstate, rt/secondary_imu, Dex3 state; applies rt/lowcmd
  • Real-time pacer, lowstate heartbeat, elastic band for hand-over
  • Ground-truth server and head/chase cameras
Working alone · RTF 0.97–1.0

P2 · gear_sonic_deploy

sonic/ · WBC @ b042411 · TensorRT 10.13.3.9
  • NVIDIA's controller binary, unmodified; zmq_manager input, sim mode on lo
  • Kinematic planner (10 Hz) plus SONIC encoder/decoder policy (50 Hz)
  • Runs on wall-clock time; exits if lowstate is absent for 500 ms
Stands · walking falls in MuJoCo ref

P3 · wl-body

body/ · /work/worldline-g1/.venv (py3.11)
  • Drive API and BodyClient; one motion at a time, newer commands pre-empt
  • A* on the 5 cm occupancy grid, pure pursuit, stuck and arrival detection
  • SonicMux: byte-exact port of upstream message framing; converts world directions to SONIC's planner frame
Written · tested on fakes

Start-up and stopping

  1. P1 starts with the robot held by the elastic band and prints WL_ISAAC_READY once lowstate is flowing.
  2. P2 starts, connects to lowstate and waits (Init Done).
  3. stand sends command{start}, holds planner IDLE, releases the band over 1 s and checks the pelvis stays at 0.55–1.0 m.
  4. walk, turn_to and go_to send planner commands at 50 Hz.
  5. stop is planner IDLE: SONIC keeps balancing.
  6. Shutdown re-engages the band, then sends command{stop}, which makes the deploy damp and exit.

Hard constraints

Real time. SONIC runs on the wall clock, so Isaac must simulate at least as fast as real time (RTF ≥ 1). A heartbeat re-sends the last lowstate if a render stalls, because 500 ms without it ends the deploy.

Never command{stop} for a user stop. It collapses the robot and the deploy process exits; only a restart recovers.

One sender to SONIC. Port 5556 has a single binder (SonicMux). Navigation and, later, GR00T manipulation take turns through it.
